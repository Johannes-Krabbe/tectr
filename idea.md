# tectr

A fast desktop and mobile app for running, watching, and steering many coding agents in parallel.

## The problem

Coding agents like Claude Code and Codex are most useful when several of them work at once, each on its own task. In practice that means juggling terminal tabs, tmux sessions, and git worktrees. You lose track of which agent is working, which is waiting on a permission prompt, and which has finished. Once you step away from the desk, you can't follow along or unblock anything.

## The idea

tectr is a single place to run all of your agents:

- **Organized by device, workspace, and topic.** A workspace is a repo on one device, so the same repo on two devices is two workspaces. A topic is a feature or task inside a workspace. It works in one folder at a time, the repo or a git worktree, and can move between them, so a discussion at the repo root can become the implementation in a worktree. Each topic holds tabs: agents, diffs, and terminals side by side.
- **Many agents in parallel.** Topics run independently, across as many workspaces and devices as you like.
- **See everything at a glance.** A sidebar sorted by device shows each agent's state live (working, waiting for you, done, failed) across all workspaces and topics.
- **Full control, not just monitoring.** Send prompts, answer the agent's questions, interrupt, and resume, all from the app. Agents run in auto mode by default, or in yolo mode if you configure it.
- **Keyboard first.** Everything on desktop can be done from the keyboard, including creating workspaces and topics with just a name and sensible defaults.
- **Desk and pocket.** A desktop app and a native iPhone and iPad app with nearly the same features, so everything can be done from either. Both are views of the same live sessions.
- **Agent-agnostic.** Claude Code first, with Codex, Gemini CLI, and others behind the same interface.
- **Fast.** Instant startup, no lag while output streams, and smooth scrolling through long sessions, in the spirit of Zed.

## Core features

1. **Workspaces and topics**: add a workspace on a device from an existing repo, a git URL, or a new repo, then create topics inside it.
2. **Tabs**: open agents, diffs, and terminals as tabs in a topic, with an optional split to see two at once.
3. **Sessions**: create, run, pause, resume, and archive agent sessions, each as a tab in a topic.
4. **Live transcript**: streaming messages, tool calls, and results, with clear rendering of markdown, code, and diffs.
5. **Worktree lifecycle**: create as many branches and worktrees as a topic needs, review the diff, merge, and clean up. This builds on what twig does today.
6. **Diff review**: a major feature. Inspect what a topic changed before merging, per file and per hunk, leave comments on many things as you go, then send them all at once.
7. **Notifications**: push alerts when an agent needs input or finishes.
8. **Multiple agents**: choose the agent per tab, for example plan with Claude and implement with Codex.

## Tech stack

- **Desktop app**: Tauri with React and Base UI
- **iOS app**: Swift with SwiftUI, on iOS 26 and later
- **Daemon**: Rust
- **Client engine**: `engine`, a Rust library embedded in both apps. The Tauri app calls it from its Rust side, and the iOS app calls it through Swift bindings generated by [UniFFI](https://github.com/mozilla/uniffi-rs).
- **Protocol types**: a Rust crate shared by the daemon and `engine`

## Architecture (high level)

tectr natively supports multiple machines without a central server in the data path. Each client connects directly to every daemon and merges the results into one view.

```
 ┌──────────────┐             ┌──────────────┐
 │ Desktop app  │             │ iOS app      │
 │ (Tauri)      │             │ (SwiftUI)    │
 ├──────────────┤             ├──────────────┤
 │ engine       │             │ engine       │
 └──┬───────┬───┘             └──┬─────┬─────┘
    │       └───────────┐ ┌──────┘     │
    │ loopback          │ │ iroh       │    websocket (tectr event schema)
 ┌──┴─────────┐      ┌──┴─┴───────┐  ┌─┴──────────┐
 │ daemon     │      │ daemon     │  │ daemon     │
 │ (laptop)   │      │ (desktop)  │  │ (VPS)      │
 └──┬─────────┘      └──┬─────────┘  └─┬──────────┘
    │ ACP (JSON-RPC over stdio)
    │
 claude-agent-acp, codex, other ACP agents
```

- **Daemon**: runs on each machine, owns that machine's workspaces, topics, sessions, and terminals, and spawns agents in their worktrees. It speaks the [Agent Client Protocol (ACP)](https://zed.dev/blog/claude-code-via-acp) to the agents and exposes one stable event schema to clients. Each daemon is the single source of truth for its own workspaces, so clients can come and go.
- **Agents via ACP**: Claude Code runs through `claude-agent-acp`, the Agent SDK-based adapter that Zed uses. tectr gets structured streaming, tool calls, and permission requests without reimplementing each agent's quirks.
- **Clients**: the desktop and phone apps are thin. They render daemon state and send actions back. Neither ever talks to an agent directly.
- **Client engine**: `engine` holds the logic both apps share. The UI sends it commands and subscribes to state, and never touches a socket.
  - **In the engine**: the daemon list, one connection per daemon with reconnects, protocol types and version negotiation, event resume, the merged device and workspace tree and pending approvals (using IDs in the form `(machine_id, session_id)`), the local cache of last known state, and sending actions.
  - **In each app**: rendering, layout, scroll position, secure key storage, push registration, and telling the engine about lifecycle changes.
  - **Streaming**: the engine batches updates, roughly once per frame, and sends small deltas rather than whole transcripts. This applies at both boundaries: Tauri's IPC to the webview and the Swift bindings.
- **Local use**: a client reaches the daemon on the same machine over loopback, using the same protocol. There is no extra hop or external dependency.
- **Remote access**: clients reach other daemons over [iroh](https://iroh.computer), which dials a device by its public key, connects directly when the network allows and otherwise through a relay that only forwards end-to-end encrypted traffic. Users set up nothing: there's no VPN to install and nothing to host. The goal is fast and encrypted, not hiding how much traffic flows.
- **Pairing and auth**: devices pair by QR code or a short code, and each daemon keeps a list of allowed keys, like `authorized_keys`. A connection from any other key is closed before it can do anything.
- **Other ways to connect**: identity belongs to tectr rather than iroh, so Tailscale or similar can be added later as another way to reach a device, without pairing again.
- **Offline machines**: the client caches the last known state and shows the machine as offline, with when it was last seen. Nothing new can be created on an offline machine.
- **Version differences**: daemons on different machines can run different versions, so the protocol negotiates a version on connect.
- **Phone**: iOS doesn't keep sockets open in the background, so the phone connects to daemons only while open and relies on push notifications otherwise. The app calls the engine's `suspend()` and `resume()` on backgrounding and foregrounding, and every resume is a normal reconnect from the last sequence number.
- **Push relay**: Apple's push service (APNs) requires credentials tied to the publisher's developer account, so they can't ship inside the daemon. The publisher runs one small stateless relay, and users host nothing. Daemons encrypt payloads so the relay never sees their contents. If the relay is down, only notifications are lost. The phone decrypts in an iOS notification extension, a separate process with tight memory limits, so decryption lives in its own small crate rather than loading the full engine.

### Why no central server

Routing everything through a server (client => server => daemon => agent) would make local use depend on a remote machine. A server or internet outage would cut you off from agents on your own laptop, a local app would require hosting a server first, and the server would see all code and transcripts and could approve tool calls on every machine.

### Possible later additions

- **Self-hosted relay**: point iroh at your own relay instead of the public default, so no third party relays your traffic.
- **Hub for team views or a web client**: an optional aggregator that connects to daemons as a client and offers the same protocol to apps, which treat it as just another daemon.

## What "fast" means here

- The transcript is virtualized, so only visible messages are rendered.
- Markdown is parsed incrementally as tokens stream in, and updates are batched per frame.
- Syntax highlighting and diffing run off the UI thread.
- The client caches each daemon's last known state, so opening the app is instant even when daemons are remote. It then catches up from the daemons in the background.

## Non-goals (for now)

- Replicating Claude Code's terminal TUI. tectr is its own GUI.
- Being a code editor. tectr is for reviewing changes, not writing code by hand.
- Cloud-hosted agents. Everything runs on machines you control, with your own credentials.

## Open questions

- **Auth and terms**: confirm what Anthropic's terms allow when a third-party client drives Claude Code with a claude.ai subscription rather than an API key.
- **Relationship to twig**: twig is written in Go and the daemon in Rust. Should the daemon call twig as a separate process, or reimplement its worktree logic?
- **Desktop layout**: the desktop UX isn't settled.

## First milestone

A daemon that can:

1. Start a Claude Code session through ACP in a fresh worktree.
2. Stream its events and relay a permission request.
3. Accept a prompt from a minimal client.

This proves the core loop before any real UI work.

The minimal client is a small CLI built on the `engine` crate, which tests it before any UI exists. Soon after, a bare SwiftUI screen showing the session list tests the Rust build for iOS and the generated bindings, to catch iOS problems early.

Four requirements apply from the start, because they are expensive to add later:

- **Machine-scoped IDs**: each daemon has a stable `machine_id`, included in session IDs and events.
- **Resumable events**: each session's events have a sequence number, so a client can reconnect and ask for everything after N.
- **Multiple connections**: the minimal client is built around a list of daemons, even if the list has only one entry at first.
- **Version negotiation**: the first handshake includes a protocol version.

Pairing, remote connections, and the push relay can wait until after this milestone.
